# State

`.warp/` is the checkpoint. `/warp-init` gitignores `.warp/config.yaml` and token files. The beam, journal, STATUS, and BOARD are committed with `state_commit.py commit` so the next cloud agent sees who is in flight, which locks are held, and which tickets are parked. Tokens, cost, API keys, and webhook URLs are stripped from that commit. Do not commit `.env` or MCP tokens; Warp never writes those.

```
.warp/config.yaml          caps, model, messenger, connector names
.warp/beam.json            tickets, gates, agents, metrics. The orchestrator is the only writer.
.warp/agents.json          the one registry of parent, Shuttle, listener, and Bugbot agents. Committed with the beam. No API key.
.warp/tickets/<id>/state.json   one ticket's current state. That Agent writes it. It may merge.
.warp/tickets/<id>/log.jsonl    one ticket's append-only mini log. That Agent writes it. It may merge.
.warp/journal.jsonl        append-only events
.warp/events.jsonl         one line per ticket status, bugbot, ci, alarm, or usage event
.warp/warp-complete.html   completion report, written when the run finishes or is stopped
.warp/BOARD.md             generated
.warp/board.html           generated
.warp/STATUS.md            generated by /warp-status
.warp/status.json          generated by /warp-status
.warp/scan.json            folder and plan the last scan used
.warp/outbox.md            Herald fallback if a messenger is down or no channel is set. Also a failed Jira move.
.warp/notify-post.json     Last Herald payload (init, scan, a failed Jira move, or an inbound ack) and where to post it
.warp/inbound-ack.json     Ack for the latest warp: command. Herald posts this before the action
.warp/listener.json        Last finished listener poll: agentId, lastPollAt, reason (polled or returned). The next poll is due pollSeconds after it
.warp/spawned.json         Local IDE hook marks only: which subagent each launch started. Cloud runners never write it. Not committed
.warp/recovery.json        Herald lines when the watchdog replaces a dead Shuttle
.warp/alarm-repair.json    Herald lines when the parent starts, advances, or gives up a lock-escape repair, and when that pass turns a gate green
.warp/pending-commands.jsonl  Channel lines waiting for inbound.py apply-pending. A message id is applied once
.warp/jira-map.json        plan id to issue key, with source and confidence. Wins over jiraKeyMap.
.warp/jira-resolve.json    JQL for the external-id, label, and remote-link lookup
.warp/jira-search.json     JQL for a summary search from map --search
.warp/jira-todo.json       Actions the current turn must do: transitions and comment bodies
.warp/jira-view.json       Tool calls for /warp-jira-view
.warp/jira-match.json      Bounded summary queries for /warp-jira-match
.warp/jira-match-report.json  Last summary match, including candidates
.warp/jira-external-id.json   External ID write queued by scan, catchup, or /warp-jira-external-id --apply --yes
.warp/jira-field.json      External ID field present or missing for a project, with checkedAt
.warp/jira-project.json    Visible projects and probe queries
.warp/version              One line, the plugin version init recorded from .cursor/plugins/warp
```

`listener` on the beam is the one channel listener for the parent turn, not one per ticket. The listener is a Subagent of the parent. Start one subagent per ticket in its own worktree, in parallel up to maxAgents. Optional `launch: agent` prints an IMPLEMENT prompt for one new Agent. A worktree subagent writes `.warp/tickets/<id>/state.json` and `log.jsonl` into this checkout by absolute path, so the parent does not fetch that state. The listener is not a separate Agent. It is one poll: it reads Slack and Teams once, queues each `warp:` command, records the poll, and returns `listen: <count>`. It does not loop and it does not sleep. `state` is `running` while one poll is out, and `stopped` between polls and while the run is paused or stopped. `agentId` is `listener` for a poll the parent started. `pollStartedAt` is set when `orchestrator.py supervise` prints `listener: poll`, and cleared by `inbound.py polled`. `lastSeenAt` is when the last poll finished. `cursor` is the newest message the last poll read, when it reported one. The next poll reads from there. `lastCount` is how many `warp:` commands the last poll queued. `polls` counts the polls issued. `startedAt` and `stoppedAt` are when the last poll started and ended. `.warp/listener.json` is the last finished poll off the beam: `agentId`, `lastPollAt` (the same time as `lastSeenAt`), and `reason`. `reason` is `polled` when `inbound.py polled` wrote it, and `returned` when the listener came back without recording the poll and `supervise` recorded it. `supervise` issues the next poll when `lastPollAt` is more than `pollSeconds` old. A poll that never reports is issued again after `listenerStaleMinutes`, and the journal gets a `listener-poll-lost` line. `listener: none` means no `slackChannel` or `teamsChannel` is set, and then no poll is ever issued. `/warp-start` and `/warp-resume` do not claim a listener. `/warp-pause` and `/warp-stop` close the poll and call `inbound.py release`, which sets `state` to `stopped`. The listener must not keep reading while paused or stopped. Tickets do not grow their own listener fields. `inbound.py claim` and `inbound.py heartbeat` are only for a listener someone starts by hand. A run does not use them. `pass` on the beam is `{startedAt, count}`: when the current parent pass started, and how many passes have run. `supervise` writes it, and `orchestrator.py parent-exit --wait` returns `pass: ticket <id>` as soon as a ticket folder is newer than `startedAt`. `parentSession` on the beam is the id `scan.py start` and `scan.py resume` print as `parent: session <id>`. Close the window, open a new one, `/warp-start`. State comes from main plus ticket folders.

Plugin hooks do not run on cloud runners, and they are not required there. `scripts/resume_hint.py` prints the resume hint (paused, done/total, ETA, alarms) and does not dispatch. `/warp-start`, `/warp-resume`, and `/warp-status` print it. `scripts/session_note.py` appends `session-stop` or `subagent-stop` to `.warp/journal.jsonl`. `/warp-stop` and `/warp-pause` append `session-stop`. A Shuttle appends `subagent-stop` when it finishes. A second note of the same type is skipped while it is still the last journal line. The beam stays the source of truth. Local hooks in `hooks/hooks.json` only repeat those scripts. Nothing depends on a hook. `hooks/subagent-start.sh` is a local IDE duplicate of the gate in `checkout.py launch`. It keeps its marks in `.warp/spawned.json`, and `WARP_SPAWN_GATE=off` turns it off. `/warp-allow-notify` still installs a local `beforeMCPExecution` hook. Cloud agents run `scripts/mcp_allow.py` and call a tool only when it prints `allow`.

The journal also records the agent lifecycle. Each line has `ts` and `type`. `paused` and `stopped` are written by `scan.py pause` and `scan.py stop`, with the reason. `beam.py pause` runs the same code and writes `paused` too. Each is followed by `session-stop`. `running` is written by `scan.py start`, `scan.py resume`, and `beam.py resume`, which set the run running through the same code. There is no `pause` or `resume` type. `reap` is written the first time an agent reads `reap: exit` against this checkout's beam: `agent`, `ticket`, and `reason`. A `--remote` check writes nothing. `reap-stale` is written when the parent records `result: <id> stopped <reason>` for an agent that is not the live Shuttle, or for an agent it cannot identify: `agent`, `ticket`, `reason`, and `live` (the row that was left running). `listener-poll-lost` is written when a poll that never reported is issued again, with the `startedAt` of the lost poll. `spawn-denied` (`role`, `ticket`, `reason`) and `subagent-end` (`role`, `ticket`, `status`, `minutes`) are written by the local IDE hooks only, so a cloud run has neither. [LIFECYCLE.md](LIFECYCLE.md) is the rule for how agents start, how they end, and how a run is torn down.

## Remote status

`.warp/agents.json` is the one registry, and the one source of truth for which agents exist. The beam carries a copy (`agentRegistry`) for the pass that is running. The file wins whenever the two differ, and the beam's copy never overwrites it. The file has two lists. `agents` records every spawn and every exit as a row: `id`, `ticket`, `role` (`shuttle`, `listener`, `parent`, or `bugbot`), `session`, `started`, `ended`, `state` (`starting`, `running`, `ended`, or `stopped`), and `endReason` (`returned`, `dead`, `replaced`, `merged`, `parked`, `paused`, `stopped`, `done`, `archived`, `polled`, or `lost`). `spawns` is one entry per Shuttle launch and per Bugbot request. `maxSpawnsPerTicket` and `maxSpawnsPerHour` count those. A listener poll is not a spawn. A Shuttle row's `id` is `subagent:<ticket>`, `shuttle-<ticket>-rN` for a replacement or a launch after a halt, or a cloud id (`bc-...`). The listener has one row for the run, `id` `listener`, not one per poll, and `polls` counts the polls it has run. A parent row's `id` is `parent:<session>`, or its cloud id on a cloud runner. A Bugbot row's `id` is `bugbot:<ticket>:<sha>`. `halted` marks a row from before a pause or a stop. It is never resumed, and its id is never reused. `reaped` is when the agent read `reap: exit`. A worktree Shuttle stamps its own row. A Shuttle on its own VM writes nothing there: the parent stamps the row whose id or `cloudId` is the `agent=` on `result: <id> stopped <reason> agent=<agent>`, or the ticket folder's `cloudAgent` when the line names no agent. A late result from a replaced VM does not stamp the new Shuttle. `cloudId` is the VM a Shuttle is on: the Shuttle writes `cloudAgent` in its ticket folder's `state.json`, and the parent binds it to the row. `retired` lists VMs the ticket left when a fix round landed on a new VM. The next pass cancels and archives them. `archivedIds` lists VMs of that row that are already archived, and `archived` marks a row whose cloud agent was archived. `superseded` marks a parent row that a later `/warp-start` or `/warp-resume` replaced. `resumedAt` is when a fix round resumed the Shuttle that had returned.

A ticket has one live Shuttle, and one cloud agent. The old row is `ended` before a replacement is recorded. `/warp-list` (`agents.py list --beam .warp/beam.json`) is how to look at the file. It prints the instance line, one `agent:` line per row, and `registry: live=<n> ended=<n>`. With `CURSOR_API_KEY` it also prints each cloud agent of this run with its status, and `out: tag [warp:<instance>] running=<n> idle=<n> kept=<n>`. It changes nothing. `/warp-cleanup` (`agents.py cleanup --beam .warp/beam.json --cloud --apply --running`) cancels and archives what `/warp-list` shows. `agents.py cleanup --beam .warp/beam.json --cloud` is a dry run: agents on this repo's origin that are in the file or whose name or prompt starts with this run's `[warp:<instance>]` tag, with id, name, repo, status, last update, link, and a count. `--apply` archives the idle ones. The agent running the command stays, and so does this run's parent. A RUNNING or ACTIVE agent stays unless `--running`, which cancels its run and then archives it. `--running` is refused while the run is running, unless `--force`. `--tag <instance>` names another run's tag in place of this one, and `--tag all` is the tag of any Warp run. `--untagged` also matches agents with no Warp tag, from before 1.5.0, loosely. One of those that is still running is left alone unless `--force`. `--all-idle` includes every idle agent in this repo. `--any-repo` does not limit to this repo. `/warp-list` takes the same selection. `/warp-pause` and `/warp-stop` set live rows to `stopped`, mark every row `halted`, and push this file to main with the beam, so a Shuttle on its own VM reads the halt. Merge and park end that ticket's rows and archive every cloud agent the ticket used. When every ticket is merged or parked, the same teardown runs once and `finishedAt` is set on the file. `CURSOR_API_KEY` is read from the environment only when a halt, a merge, a park, a retired VM, or cleanup cancels or archives a cloud agent. It is never written into this file. Close the window, open a new one, `/warp-start`. State comes from main plus ticket folders, including this registry when `state_commit.py` committed it.

The claim goes in. The launch snapshot of `.warp/beam.json` is committed onto the ticket branch so the Agent can read its claim. That file is not a live feed. The Agent does not commit updates to it, and a merge onto the base branch does not take it. The orchestrator keeps the live beam.

Status comes out in `.warp/tickets/<id>/`. Only that ticket's Agent writes that directory. Other tickets' directories are never touched, so committing and merging one does not interfere with another.

`state.json` holds the current state and the timestamps: `startedAt`, `updatedAt`, and `heartbeatAt`. It also holds the pull request, the check result (`result`, `name`, `log`), the error text, the alarm reason, and `escaped` paths. On a dedicated VM it also holds `cloudAgent`, that VM's cloud agent id. The parent binds it to the Shuttle's row in `.warp/agents.json` as `cloudId`, so a pause or a stop can cancel and archive that agent by id. `log.jsonl` is append-only. Each line has `at`, `state`, and `error`. States include `started`, `heartbeat`, `planning`, `coding`, `review`, `bugbot`, `fix`, `pr-opened`, `check-red`, `check-green`, `lock-escape`, `alarm`, `failed`, and `done`. A `lock-escape` line includes the escaped paths.

The Agent commits and pushes only that directory when the state changes, and on a heartbeat at least every 5 minutes (`ticket_state.py append --push`). After it writes, `append` prints the reap line: `reap: continue`, or `reap: exit <reason>`. On `reap: exit` the Agent stops and returns `result: <id> stopped <reason> agent=<agent>`. `<agent>` is its registry id or its cloud id.

Every orchestrator tick fetches each in-flight branch and reads only that ticket's directory. `ticket_state.py observe` patches the live beam for that ticket id. Lines whose id is some other ticket are ignored. A second tick is idempotent. The branch beam is not copied over the live beam. An in-flight branch is not rebased. Paused and stopped runs do not fetch and do not relaunch.

The parent reads three signals from that directory, plus the provider when the directory is silent:

- Death: `heartbeatAt` (or the last `heartbeat` line). If there is no heartbeat, the launch time on the live beam (`workerStartedAt` or `claimedAt`). Older than `staleMinutes` means the worker died. One subagent starts again on the same worktree and branch. Branch, pull request, locks, and `jira.startedAt` stay. Past `maxRecoveries` the alarm is `worker-died`.
- Checks: a `check-red` or `check-green` line, or `check.result` on `state.json`. `make ci` and Bugbot show up here. Check-red sends the ticket back. Past `maxFixAttempts` (default 5) the ticket parks. If the directory never recorded a check, the provider pull-request rollup is used. A dead Agent that already opened a pull request still reports check-red or check-green.
- While the Agent is alive: `planning`, `coding`, `review`, `bugbot`, and `fix` on `state.json` and in the log.

A `lock-escape` line is an alarm with the escaped paths even though the Agent has exited. The repair pass widens the lock from `escaped`. The parent does not wait for the Agent to still be running.

Herald posts one line when a remote event changes the live beam (`herald: <id> <state>`) and when an Agent is declared dead (`<id> worker died. A new Shuttle started.`).

## Ticket status

`queued` → `claimed` → `planning` → `coding` → `review` → `bugbot_running` → (`fix` → `bugbot_running`)* → `awaiting_approval`? → `merging` → `merged` → `done`

The parent stores a `phase` on the ticket and drives it inside `orchestrator.py supervise` and the dispatch tick: `implementing`, `pr-open`, `reviewing`, `fixing`, `ready`, `merging`, then `merged` or `parked`. Opening a pull request is not done. The Shuttle runs `checkCommand` and writes `pr.acResults` for every acceptance criterion. `bugbot: request <id> <url>` asks Bugbot on the pull request. A finding, red CI, or a failed criterion starts `step=fix` on the same branch. Past `maxFixAttempts` (default 5) the ticket parks. The merge runs on every supervise pass when Bugbot is finished with no unresolved findings, the rollup is green, the acceptance criteria pass, and the size is in `autoMergeSizes` or someone has proceeded. After the merge the pass prints `herald:`, `jira: MUST DO`, `slack:`, and `beam: push`, then starts the next ready ticket up to `maxAgents`. `/warp-start` and `/warp-resume` adopt an open pull request into `reviewing` or `fixing`. `checkout.py verify` raises `lock-escape`, and that supervise pass calls `alarm_repair.py next`.

`openWork` on the beam is that same list for a new session: every ticket that is not merged, with state, step, age, last active time, pull request, Bugbot, CI, acceptance, stall, retries, alarm, and the next action. `/warp-status`, `/warp-start`, and `/warp-resume` print it, alarms and stalls first, then a count of each state. `maxInProgress` (default 20) is how many tickets may be open at once: started, and not merged or parked. It holds only new tickets. It does not stop a fix, a rebase, or a relaunch. Each of those is an agent like any other and takes a `maxAgents` slot. `maxAgents` (default 18) is the one cap on agents that run at once. Parked, merged, and queued tickets do not count. `/warp-status`, start, and resume print `in progress N/maxInProgress`, or `holding new launches (N/maxInProgress), N fix workers running` when that cap is full, plus `live shuttles N/cap`, the fix workers that are running, and the dead tickets waiting for a replacement. The fix worker count is shown. It is not a cap. Only a live Shuttle holds a `maxAgents` slot. `/warp-start` and `/warp-resume` also print `unfinished: <n> open. ...` and start that work before any new ticket: open pull requests that need a fix, then tickets whose Shuttle was halted or died, then the ready queue. supervise marks `stalled` when the state makes no progress within its limit and appends a `stall` line to `.warp/tickets/<id>/log.jsonl`. Progress is a new commit, a phase change, or a check result change. A heartbeat, or a start that does not change those, does not reset `watch.since`. A conflict, CI that never started (`ciStartGraceMinutes`), a stale rollup, or a head sha mismatch is fixed on that pass. `watch.fixerAttempts` counts fixer passes. Past `maxStallFixes` the ticket is `parked` with `parkReason`. `postedAlarms` and `statusDigest.at` stop a repeat Slack post. Every `repairSweepMinutes` (default 15) that pass also sweeps the whole run: what is broken, and what can be fixed that is not already queued or running. Broken covers tickets, pull requests, CI on main, locks, gates, the listener, and the beam, including red or stuck CI, a merge conflict, unresolved Bugbot findings, a stale or orphaned lock, a red base, a stuck gate, an overdue listener poll, and a beam that is out of sync with main. The sweep reuses the fixer paths, starts work up to the slot cap, and logs findings and actions. `/warp-status` shows the last sweep. Slack is posted only when the sweep starts something new or escalates.

Side exits: `blocked` (human hold), `alarm` (needs a human), `skipped`. `recovering` is still in flight: the Shuttle died and one replacement is reserved. It holds the same locks. It is not a second claim.

Jira keys: `jiraKey` is the real issue key (`WAR-1`), never the plan id (`WV-01`), unless that id's project prefix matches `jiraProject` or `jiraKeyPrefixes`. It is set from a Jira export `key`, a `schedule.json` `jiraKey`, a markdown `Jira:` line, `Jira Key` column, or `[WAR-1]` heading, `.warp/jira-map.json`, `jiraKeyMap`, `beam.py set --jira`, or one exact Jira match. A Jira JSON import's `externalId` is the plan id, not this field. `jiraMapping` is `mapped`, `ambiguous`, or `needs mapping`. `jiraKeySource` is `plan`, `export`, `map`, `manual`, `external`, `label`, `link`, `summary`, or `inferred`. `jiraKeyConfidence` is `high` for an external-id field or an exact summary, `medium` for a label, a remote link, or a 60-character prefix, and `low` for a fuzzy summary stored with `--yes`. `.warp/jira-map.json` stores the same key, source, and confidence. A manual key is never overwritten. Two matches set `jiraKeyCandidates` and do not pick a key. A rescan keeps a manual key and reapplies the map file. `jira.id` and `jira.cloudId` are written by `resolve --ticket`. `jira.externalId` is the plan id once a key is stored. It is the value we want on the issue, not proof Jira holds it. `jira.externalIdOnIssue` is the last value seen on the issue (`""` empty, absent means unknown). `jira.externalIdWritten` is `{value, at, method}` after the plan id was stored on the Jira issue. `method` is `field`, `label`, or `remote-link`. A second write is skipped. `jira.externalIdAttempt` is `{at, result, error, event: "external-id"}` when that write was skipped or failed. It does not replace `jira.lastAttempt`. A missing External ID field is remembered in `.warp/jira-field.json` (`status`, `project`, `checkedAt`, `fingerprint`) so later scans print one summary. `/warp-jira-check` prints `jira mapping:`. `jira.startedAt` and `jira.previousStatus` are set when Warp moves an issue to In Progress. The first claimed ticket of a run is a claim made while no ticket has `jira.startedAt`: no earlier ticket was linked and moved to In Progress. If Jira returns not found, or no real issue key can be resolved, and `jiraTransition` is true, Warp sets that ticket back to `queued`, clears `agent`, `branch`, `jira.startedAt`, and `jira.previousStatus`, and stops the run (`runState: stopped`, the same session note as `/warp-stop`). `jira.lastAttempt` still records the miss. A later miss, after any ticket has `jira.startedAt`, is a per-ticket alarm: the claim stays and the run continues. `jiraTransition: false` does not stop the run. `jira.qaReadyAt` is set when a manual-path ticket reaches QA Ready, `jira.doneAt` when a merge moves the issue to Done (auto-merge, and manual merge when `jiraDoneOnManualMerge` is true), and `jira.lastSync` holds the last result. A beam status of `merged` with an empty `jira.doneAt` is `merged-but-not-done` on `/warp-jira-check`. `jira.lastAttempt` is `{event, result, error}` from `record --result failed --error "..."` and does not set `startedAt`. `jira.comments` and `pr.comments` map an event (`claim`, `pr-opened`, `qa-ready`, `merged`, `bugbot`, `bugbot-rerun`, `ci`, `alarm`, `blocked`) to `{at, id}` so a retry does not post it again. `autoMerge` on the ticket, set by `beam.auto_merge` from the size and `autoMergeSizes`, chooses QA Ready or Done. A size in the list does not move to QA Ready. `/warp-jira-check` (`jira_sync.py verify`) prints, per ticket, what should have happened and which of these fields are empty.

`merged` and `done` both unblock dependents and drop locks, because locks are held only while the status is active. `pr.sha`, `pr.mergedAt`, `pr.via` (`local` or `connected`), `pr.mergeMethod`, `pr.approvedBy`, and `pr.proceededBy` record the merge. `done` means Jira was transitioned. Reed sets `merged`, which prints the post-merge MUST DO, then the agent records the Jira move. If Jira fails, the ticket stays `merged` and `/warp-jira-check` catch-up retries the transition. `.warp/STATUS.md` done rows and `.warp/BOARD.md` merged rows show the sha and whether Jira is Done.

## Fields that matter

- `instance` — `id`, `host`, `machine`, `createdAt`. Six characters that name this Warp run. `/warp-start` sets it once, and a later start or resume, from any window or VM, keeps it. On a cloud runner `id` is the last six characters of the parent's cloud agent id (`machine`). On a laptop it is six characters of a hash of the machine id and the beam's path. Every agent the run starts is named `[warp:<id>] <ticket> <step>` or `[warp:<id>] listener`, every Slack and Teams header ends with `warp:<id>`, and `status.json` has an `instance` object with `tag`, `id`, `host`, and `machine`. Pause, stop, `/warp-list`, and `/warp-cleanup` match that tag, so another Warp run's agents are never touched.
- `deps`, `locks`, `gate`, `critical`, `rankDays` — from the schedule, not edited live. A gate's `status` is `pending`, `green`, or `red`. A pending gate, or a stale red gate with no check that is actually red, becomes `green` when every member is `merged` or `done`, or when every ticket on the beam is. Then the tick runs. `evidence` is `members merged:` and those ids. G1 with members P-002, P-003, P-004, and P-018 stores `members merged: P-002, P-003, P-004, P-018`. Herald posts `G1 pending cleared. Members merged. Tick ran.` `greenAt` is when that happened. A green gate is not set back to pending. Evidence that names a red check, or a member CI, Bugbot, rollup, or checkCommand that is red, keeps the gate. The name alone is not a red check. The tick does this, and so does the parent's repair pass when the ready set is empty. `beam.py gate` can still set `red` or `green` with evidence.
- `autoMerge` — true when the size is in `autoMergeSizes`. Both paths wait for Bugbot and CI. This flag chooses auto-merge or `awaiting_approval`. `bugbotManual` applies only when the flag is false.
- `pr.bugbot` (`pass` or `fail`), `pr.bugbotEvidence`, `pr.bugbotFindings`, `pr.bugbotFixed`, `pr.ci` (`green`), `pr.approvedAt`, `pr.reviewedSha`, `pr.rerun` (`new-commits`), `pr.url`. `pr.bugbotFindings` is a list of finding strings. A dict finding stores its message, or else its body. A count above 0 is stored as `N Bugbot findings (details not loaded)` and keeps the merge gate closed. 0 and false are no findings. `pr.headSha` is the commit those results belong to, with `rollupSha`, `ciSha`, `checkSha`, `bugbotSha`, and `bugbotFindingsSha`. A result from an older sha does not block the new head, and Bugbot is requested again. `pr.conflict` is the conflicting file list, or true when GitHub reports `mergeable` CONFLICTING or `mergeStateStatus` DIRTY and the file list is empty. That pass starts a rebase. `pr.behind` is a BEHIND merge state. `pr.ciAbsent` means the head has zero check runs after `ciStartGraceMinutes`. `pr.acResults` is copied from the Shuttle `RESULT.json` (`tasks/<id>/RESULT.json` or `.warp/tickets/<id>/RESULT.json`) when the beam never got it.
- `bugbot_running` — Bugbot is in progress again after new commits landed on a ticket that was already `awaiting_approval`. Jira is left at QA Ready.
- `attempts`, `tokens`, `minutes`, `alarm`, `jiraKey`.
- `lastSeenAt` — Shuttle heartbeat. `agent` is the agent id that owns it. Written by `beam.py heartbeat` at claim, at each status change, and on a short interval while that turn is alive (at least every 5 minutes, and always inside `staleMinutes`). A heartbeat is not a timer: the Shuttle writes it between steps of work it is already doing. `beam.py heartbeat` prints the reap line after it writes.
- `claimedAt`, `workerStartedAt` — when this claim started, and when the current worker started. A recovery sets `workerStartedAt` and clears `lastSeenAt`. The original `claimedAt` stays.
- `recoveries`, `recoveredAt`, `recoveryPriorStatus` — how many times this ticket's Shuttle was replaced, when, and the status to resume (`coding`, `fix`, and the other Shuttle statuses). Past `maxRecoveries` (default 5) the next death sets `alarm` to `worker-died` and does not start another. `needsReplacement` is true while the ticket has no live Shuttle and waits for one. A halt (`/warp-pause` or `/warp-stop`) sets `needsReplacement` and `haltResume` on every ticket that had a Shuttle out, and frees its slot. `haltResume` makes the next launch a resume after a halt: a new Shuttle with a new agent id on the same branch (`fix: <id> resume after halt`). The status passes through `recovering`, but `recoveries` is not counted and no one is told a worker died.
- `escaped` — paths outside the lock, stored with a `lock-escape` alarm (`beam.py set --escaped`, or `alarm_repair.py paths`). The parent's repair widens `locks` to these paths.
- `addedLocks` — paths the current repair added. The Herald start line names the same paths.
- `alarmRepairs` — how many lock-escape repairs have started. Past `maxAlarmRepairs` (default 5) later passes skip the ticket.
- `alarmRepair` — `{state, attempts, added, agent, ...}` for the repair in flight. `state` `working` is the repair Shuttle. `naming` on the beam's `alarmRepair` record means an older alarm still needs its path list. The beam's `alarmRepair.active` is the one repair in flight. `alarmRepair.tried` is the tickets already taken in this pass.
- `events` — append-only list on the ticket. Each row is `{at, type, ...}`. `type` is `status` (`from`, `to`), `bugbot`, `ci`, `alarm`, or `usage`. The same row, plus `id`, is appended to `.warp/events.jsonl`. Old beams without `events` still render. The timeline uses these rows and does not invent a claim time.
- `usage` — `{tokensIn, tokensOut, tokensCached, cost}` from `beam.py usage` or the same flags on `set`. Each flag replaces that field. It is not added to the previous number. `tokens` and `minutes` from `spend` stay a separate additive total.
- `pr.ciRetries` — how many times CI was recorded as something other than `green`.
- `runStartedAt` — first status that leaves `queued` or `skipped`. `runEndedAt` and `reportGeneratedAt` are set when the completion report is written. `runComplete` is true after that write and cleared on the next start. `stoppedAt` is set by `/warp-stop` and cleared by the next `/warp-start` or `/warp-resume`. `/warp-pause` does not set it. A beam that ingest left at `runState: stopped` has no `stoppedAt`, so a claim does not count as the run ending.

## Restart

The orchestrator is the only merger. On start or resume it rebuilds from git before dispatch. `orchestrator.py rebuild --facts` classifies each ticket: `merged` when the work is on the base branch, `in-flight` when that ticket has an open branch or pull request, and `pending` otherwise. An explicit `parked` ticket stays parked. Then the dispatch loop runs. Ready means every blocker is merged on the base branch and no lock overlaps an in-flight ticket, including a parent folder. The merge queue is serial. Past `maxFixAttempts` (default 5) the ticket parks. A red base branch stops merging. Sizes outside `autoMergeSizes` still wait for `/warp-proceed` or `warp:proceed`.

`checkCommand` (empty by default) is the rebase check. When it is empty, Bugbot and CI as configured are the required checks. `make ci` is kept as the full check command; the space stays. Its result is `pr.check`. A red result is stored and the ticket is sent back with the log (`send-back <id> fix` and a `start` line). Past `maxFixAttempts` (default 5) the ticket parks. A green result is not a failure. The name alone is not a red check. `appendOnlyPaths` (empty by default) lists shared files whose conflicts keep both sides. A Shuttle that exits with a pull request records `pr.opened`. The slot stays occupied until the GitHub or Bitbucket check rollup (`pr.rollup`) is green. Locks stay until merge or park. Bugbot runs on the pull request after push, not inside the VM. `mergeQueue` defaults to false. The cap is `maxAgents`. A project may set 18. `agent` is the cloud agent id. `worktree` is the local git worktree path. Never two agents on one ticket, and never two tickets in one VM or one worktree. On a cloud runner, `/warp-start` refuses when `transitionJiraIssue`, `addOrEditJiraIssueComment`, or `slack_send_message` is missing from the MCP allow list. `--force` starts anyway. A local runner does not block. `/warp-upgrade` replaces `.cursor/plugins/warp` and does not rewrite this beam. When the source is a git checkout it fetches the default branch. If the fetch fails, it prints `fetch failed` and `keeping the installed copy`. `/warp-init` does not upgrade an existing copy. `--force` is not an upgrade flag. The flags are `--root` and `--source`. It prints `Warp vX.Y.Z`. Confirm with `/warp-version`. Init and upgrade write `.cursor/commands/warp-upgrade.md` from `commands/warp-upgrade.md` so a reload lists `/warp-upgrade` when the plugin command index still omits that path.

1. `scripts/resume_hint.py` prints done/total and the pause flag. Cloud runners run this from the Warp commands. A local sessionStart hook only repeats it.
2. `/warp-start` and `/warp-resume` run `beam.py watchdog` from `scan.py`. Every Warp tick runs it before `ready()`. Plugin hooks do not run on cloud runners. A dead turn does not notify Warp, and Cursor does not restart it.
3. Warp reconciles PRs before `ready()`.
4. A Shuttle whose branch exists continues that branch. A dead Shuttle stays on that same branch.

A Shuttle is dead when `lastSeenAt` is older than `staleMinutes` (default 15), or it never heartbeated and the claim is older than `staleMinutes`. A fresh heartbeat means alive: do not start a second worker. Paused and stopped runs do not recover and do not start a replacement.

The listener is a Subagent of the parent turn, and it is one poll. The watchdog prints no listener line and never starts a listener. `orchestrator.py supervise` issues each poll (`listener: poll`), and a poll that never reports is issued again after `listenerStaleMinutes`. If the parent's turn dies, nothing restarts it: run `/warp-resume`. Close the window, open a new one, `/warp-start`. State comes from main plus ticket folders. Every merge and the end of each parent tick commit the live beam onto main. The ticket branch's beam is not the copy that lands. `/warp-update-state` loads that beam from main, patches `.warp/tickets/<id>/` only, puts back pause, stop, claims, and runState the parent has that main does not, and pushes. `/warp-pause` and `/warp-stop` run that sync before they return. Each ticket is a subagent in its own git worktree, or on its own VM when `subagentVm` is true.

Dead Shuttle (`claimed`, `planning`, `coding`, `fix`, or already `recovering`): the launch slot is released immediately. It does not count as a live Shuttle. Branch, pull request, `jira.startedAt`, and locks stay. The ticket is not queued, so `ready()` will not hand the same files to someone else. On start or resume, a fresh heartbeat stays. A stale heartbeat needs a replacement, and Warp starts as many as `maxAgents` allows. Dispatch exactly one new Shuttle for each `shuttle: replace <id>` line. Status becomes `recovering` when that replacement starts. Herald posts one line: `<id> worker died. A new Shuttle started.` The replacement heartbeats, then sets status back to `recoveryPriorStatus` and continues the branch. Past `maxRecoveries`, status is `alarm` and `alarm` is `worker-died`. Do not start another.

`stuckAfterMinutes` is a different signal (no beam update, and not waiting on approval). It does not release a lock. `orchestrator.py supervise` restarts that step up to `maxRecoveries`.

Lock-escape repair is separate from worker death. The parent tick calls `alarm_repair.py next` while the run is running, one ticket at a time, every `alarmRepairMinutes` (default 15), up to `maxAlarmRepairs` (default 5). The listener does not start the repair Agent. It widens that ticket's locks to the paths on `escaped` and starts one repair Shuttle. It waits when an in-flight ticket holds one of those paths. `bugbot-failed`, `worker-died`, `stuck`, `ci-red`, and `gate-red` are left alone by `alarm_repair.py`. `orchestrator.py supervise` restarts a `worker-died` step, starts a fix Shuttle for `ci-red` and `bugbot-failed`, and restarts `stuck` up to `maxRecoveries`. `gate-red` stays on the gate. Pause and stop do not repair. `.warp/alarm-repair.json` holds the Herald lines from the latest repair change.

Pause sets `paused: true` and `runState: paused`. Stop sets `runState: stopped`. Both run the same teardown. One thing differs: stop also writes the completion report and records `stoppedAt`. Every row in `.warp/agents.json` is ended and marked `halted`, every Shuttle slot is freed, the listener's poll is closed, and each ticket that had a Shuttle out gets `needsReplacement` and `haltResume`. The beam and the registry are pushed to main. `ready()` returns nothing. The watchdog prints `watchdog: skipped (paused)` and changes nothing. Ticket status, branches, worktrees, pull requests, locks, and `jira.startedAt` are kept. Nothing from before the halt is resumed. `/warp-start` and `/warp-resume` are the same command, from a paused run or a stopped run. Either one launches a new Shuttle with a new agent id on the same branch (`fix: <id> resume after halt`), before any new ticket. That is not a recovery.

## Invariants `beam.py check` enforces

- Every dep exists.
- No dependency cycle.
- No two active tickets with overlapping locks.

A failed check aborts the tick.
