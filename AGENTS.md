# Warp agents

The orchestrator is the only merger. It reads `maxAgents`, `checkCommand`, and `appendOnlyPaths` from config. A project may set `maxAgents` to 18. Shuttles do not merge.

Every pull request bumps the patch version and adds a changelog entry.

- One ticket, one checkout. `subagentVm` defaults to false. `runner: local` forces it false and forces `launch` to `worktree`, skips the cloud-environment start check, and logs one note. Start, `/warp-version`, and status print the effective values. `maxLocalSubagents` defaults to 18. `memoryCheck` defaults to false, so only that cap applies until `true` lets `free -g` lower it. On a cloud runner, `true` asks for a dedicated VM. The prompt says: run in your own cloud environment on a dedicated VM with its own clone and branch, not a git worktree on this machine. Start one subagent per ticket, in parallel up to `maxAgents`. The subagent fetches the latest main, clones it, and creates `warp/<id>-<jira>` itself. Its first step is `hostname` and `free -g`. It writes `.warp/tickets/<id>/` on that branch and pushes. The parent patches the beam from those folders and owns `.warp/beam.json`. A same hostname falls back to a worktree on this machine: one warning per run, then `maxLocalSubagents` (`memoryCheck` may lower it). Start one subagent per ticket in its own worktree, in parallel up to `maxAgents`, when `subagentVm` is false or that fallback happens. `checkout.py launch` then runs `git fetch origin main`, then `git worktree add <worktreeRoot>/<id> -b warp/<id>-<jira> origin/main`. `worktreeRoot` defaults to `.warp/worktrees`, which is gitignored. The prompt names the ticket, Jira key, locks, acceptance, branch, and absolute worktree path. The subagent works only inside that path, commits, pushes, and opens the pull request. It never merges, never touches the parent checkout, and never calls Jira or Slack. It writes `.warp/tickets/<id>/state.json` and `log.jsonl` straight into the parent checkout by absolute path, so nothing pushes that state around. The parent owns the beam, does all Jira and Slack work, merges serially, and pushes the beam on each merge and at the end of each tick. Cloud subagents use the MCP servers at cursor.com/agents, not this session. `/in-cloud` in the Agents Window is the manual fallback, one ticket per invocation. A cloud start warns, and `--force` allows it, when `.cursor/environment.json` and `cloudSnapshot` are both missing. `checkout.py verify` runs after the subagent. The parent checkout must be clean apart from `.warp/`, and the diff must stay inside the worktree and the locks. A miss raises `lock-escape`. Merge or park runs `git worktree remove` and `git worktree prune`. A failed subagent result raises `worker-died`. The heartbeat watchdog still covers a parent that dies mid-turn. `/warp-resume` reuses the surviving worktrees and branches. Optional `launch: agent` prints an IMPLEMENT prompt for one new Agent, for a future Cursor Cloud Agents API. This plugin does not call that API. Clone main so `.cursor` rules load, then create the branch. A beam file does not have to exist on the branch before that Agent starts. Never two tickets in one worktree, and never two workers on one ticket.
- `.warp/agents.json` records every Shuttle, listener, and Bugbot agent. A Shuttle is replaced only after its turn returned or its heartbeat is older than `staleMinutes`. Fix rounds resume that Shuttle. A ticket never has two live Shuttles. Bugbot is requested once per head commit. Spawn caps are `maxSpawnsPerTicket`, `maxSpawnsPerHour`, and `maxListenerRestartsPerHour`. Hitting a cap raises an alarm and does not spawn again. Nothing spawns while the run is paused or stopped, or every ticket is merged or parked. The listener and each Shuttle read `runState` and exit. `/warp-stop` marks every registered agent stopped. `/warp-cleanup` lists the registry. With `CURSOR_API_KEY`, `agents.py cleanup --beam .warp/beam.json --cloud` is a dry run and `--apply` archives the matches (`POST /v1/agents/{id}/archive`). A match is IDLE, on this repo's origin, and in `.warp/agents.json` or a Warp role in the name or prompt (Shuttle, IMPLEMENT, fix, rebase, listener, Warp-triggered Bugbot). The agent running the command stays. A RUNNING or ACTIVE agent stays. `--all-idle` stays on this repo. `--any-repo` with `--all-idle` is every idle agent the key can see. Without the key it prints `https://cursor.com/agents/<id>`. The key is never committed. Close the window, open a new one, `/warp-start`.
- A Shuttle that exits with a pull request has finished. The slot stays occupied until the GitHub or Bitbucket check rollup is green. Bugbot runs on the pull request after push. Locks stay until merge or park. `mergeQueue` defaults to false. When it is true, or GitHub reports a merge queue, enqueue the pull request. A direct merge that branch protection rejects is not marked merged.
- Commit the beam, journal, and STATUS/BOARD with `state_commit.py` so the next agent sees in-flight work, locks, and parked tickets. Strip tokens, cost, API keys, and webhook URLs. `.warp/config.yaml` stays gitignored. `/warp-init` replaces an old `.warp/` gitignore line and leaves other lines.
- `/warp-start` on a cloud runner refuses when `transitionJiraIssue`, `addOrEditJiraIssueComment` (Jira transitions on), or `slack_send_message` (Slack notify on) is missing from the MCP allow list. It does not claim. `--force` starts anyway. A later claim repeats the check unless the run was force-started. A local runner does not block.
- `/warp-upgrade` replaces `.cursor/plugins/warp`. Run it in the repo that has Warp installed. When the source is a git checkout, it fetches the default branch and copies that tree. If the fetch fails, it prints `fetch failed` and `keeping the installed copy`. The installed copy stays. It does not overwrite `.warp/config.yaml` or the beam. It prints `Warp vX.Y.Z`. Reload Cursor, then confirm with `/warp-version`. `/warp-init` does not upgrade an existing copy. This command does. `--force` is not an upgrade flag. The flags are `--root` and `--source`.
- The version lives in `VERSION`. `.cursor-plugin/plugin.json` must carry the same number.
- `CHANGELOG.md` needs a `## <version>` heading for that number.
- `python3 scripts/bump_version.py` bumps the patch and inserts a changelog stub. Use `--minor` or `--major` only when the change calls for it. Replace the stub with what changed.
- Do not ship a change on the current version. The next patch after 1.3.19 is 1.3.20.
- `docs/COMMANDS.md` is the command reference and `docs/CONFIG.md` is the config reference. The README command table, [docs/GUIDE.md](docs/GUIDE.md) (Jira from import to merge), [docs/RUNBOOK.md](docs/RUNBOOK.md) (transitions and nothing linked), [docs/STATE.md](docs/STATE.md), and [docs/CONNECTORS.md](docs/CONNECTORS.md) have to match the same behavior. A new flag, command, skill, or config key belongs in those files. `tests/test_docs.py` checks config keys, every `commands/*.md` name, and every `jira_sync.py` subcommand.
- Chat commands live in `commands/` and `skills/`. Agent-only skills are `shuttle-run`, `warp-dispatch`, `warp-alarm`, and `warp-listen`. `warp-listen` is the one channel listener for the beam. The listener is a Subagent of the parent. Start one subagent per ticket in its own worktree, in parallel up to `maxAgents`. It shares the parent's session and checkout. It is not a separate Agent. Exactly one listener while the loop is running. It loops: poll the channel, post acks, enqueue `warp:` commands, write `.warp/listener.json` with `inbound.py heartbeat`, shell `sleep` for `pollSeconds`, and repeat. It does not return while the loop is running. It returns on pause or stop, or returns `recycle` when its context is large. A Cursor subagent can still exit. The parent runs `orchestrator.py supervise` and starts exactly one replacement when the listener returns or the heartbeat is older than `listenerStaleMinutes`, unless the loop is paused or stopped. Each restart is logged. Herald posts one note when restarts repeat. `parent-exit` prints `parent: stay` while the listener is supposed to be running, while any ticket is not merged or parked. `parent: exit` is when every ticket is merged or parked, or the run is paused or stopped. Each pass runs supervise, fetches `.warp/tickets/<id>/` for in-flight tickets, patches the live beam, dispatches a ready slot with `checkout.py launch` and one subagent in that worktree, pushes the beam, and passes again. A launch refusal is not idle. Pause and stop still sync state, and then the listener may stop. A running flag from the previous turn does not block the next start. The listener does not implement tickets, does not merge, and does not write product code. The parent runs `inbound.py apply-pending` and patches the live beam. `/warp-start` and `/warp-resume` launch it. `/warp-pause` and `/warp-stop` stop it. Plugin hooks do not run on cloud runners. `scripts/resume_hint.py`, `scripts/session_note.py`, and `scripts/mcp_allow.py` are the path those hooks used to cover, and the Warp commands run them. Local hooks in `hooks/hooks.json` only repeat the same scripts. `/warp-allow-notify` still writes a local `beforeMCPExecution` hook; cloud agents use `mcp_allow.py` instead of that hook. A dead Shuttle or listener does not notify Warp, and Cursor does not restart it. `beam.py heartbeat` and `inbound.py heartbeat` write `lastSeenAt` and the agent id. `beam.py watchdog` runs on every tick and on start/resume. A worker is dead when that heartbeat is older than `staleMinutes`, or it never heartbeated and the claim or listener start is older than that. The listener is not a watchdog replacement. Close the window, open a new one, `/warp-start`: state comes from main plus ticket folders. A dead Shuttle becomes `recovering` on the same branch. Past `maxRecoveries` the alarm is `worker-died`. Pause and stop do not replace anyone. There is no process table and no hook for that. Ready means every blocker is merged on the base branch and no lock overlaps an in-flight ticket, including a parent folder. The slot frees when the provider check rollup is green. Locks stay until merge or park. The merge queue is serial. Past `maxFixAttempts` (default 5) the ticket parks. A red base branch stops merging. Restart classifies merged, in flight, and pending from git. Every `repairSweepMinutes` (default 15) that pass also sweeps the whole run: what is broken, and what can be fixed that is not already queued or running. Broken covers tickets, pull requests, CI on main, locks, gates, the listener, and the beam, including red or stuck CI, a merge conflict, unresolved Bugbot findings, a stale or orphaned lock, a red base, a stuck gate, a dead listener, and a beam that is out of sync with main. The sweep reuses the fixer paths, starts work up to the slot cap, and logs findings and actions. `/warp-status` shows the last sweep. Slack is posted only when the sweep starts something new or escalates. Sizes outside `autoMergeSizes` still wait for `/warp-proceed` or `warp:proceed`. `/warp-update-state` fetches origin/main, loads that beam, patches `.warp/tickets/<id>/` only, and puts back pause, stop, claims, and runState the parent has that the remote beam does not. It pushes the reconciled beam, journal, and board. `/warp-pause` and `/warp-stop` run that sync before they return. On every merge, and at the end of each parent tick, the same live beam is pushed to main. Close the window, open a new one, `/warp-start`. The parent tick repairs `lock-escape` only, one ticket at a time. The listener does not start the repair Agent, every `alarmRepairMinutes` (default 15). `alarm_repair.py next` widens that ticket's locks to the paths that escaped, up to `maxAlarmRepairs` (default 5). It waits when an in-flight ticket holds one of those paths. `bugbot-failed`, `worker-died`, `stuck`, `ci-red`, and `gate-red` are left alone by `alarm_repair.py`. `orchestrator.py supervise` restarts a `worker-died` step, starts a fix Shuttle for `ci-red` and `bugbot-failed`, and restarts `stuck` up to `maxRecoveries`. `gate-red` stays on the gate. Pause and stop do not repair. When that pass opens and the ready set is empty, it recomputes every pending gate. A pending or stale-red gate turns green when every member is merged or done and no check is actually red, then the tick runs. G1 with members P-002, P-003, P-004, and P-018 stores `members merged: P-002, P-003, P-004, P-018`. Herald posts `G1 pending cleared. Members merged. Tick ran.` and the pass dispatches. Every tick recomputes before `ready()`. A green gate stays green. Pause and stop do not recompute. `make ci` is kept as the full check command. A red result is stored on `pr.check` and sent back to that ticket with the log (`send-back <id> fix` and a `start` line) so the run does not sit idle. Past `maxFixAttempts` (default 5) the ticket parks. The name alone is not a red check. The gate stays while that check is red.
- `python3 scripts/check_version.py` fails when the files disagree or the changelog has no entry. CI fails when the pull request version is not newer than `main`. An equal version passes when the working tree already matches `main`, which is what happens when the check starts after the merge.
 Init and upgrade write every `commands/*.md` file to `.cursor/commands/`, including `.cursor/commands/warp-upgrade.md`, so a reload lists `/warp-upgrade`, `/warp-update-state`, `/warp-status`, and the other commands when the plugin command index still omits that path.
