## 1.6.21

- New: `stateInMerge` (default `true`). With `mergeMethod: merge`, Warp merges a ready pull request with one merge commit it writes itself and pushes to the base branch: its parents are the base and the reviewed head (so GitHub marks the pull request merged), and its tree is the merge plus the run state with that ticket merged. No separate `Warp state` commit follows a merge any more (`state: in the merge commit (WE-01)`). It falls back to `gh pr merge` and a state commit when the push is refused (branch protection), the branch moved past the reviewed head, a file outside the run state conflicts, a merge queue is on, or the method is `squash` or `rebase` (`merge: <id> through the provider (<why>)`). `pr.stateInMerge` records the commit. `state_commit._build_commit` can start from a given tree and take several parents.
- New: `pushStateNew` (default `false`). In 1.6.20 every new ticket branch published the run state. Now `checkout.py launch` publishes only with `pushStateNew: true` (`state: published (started <id> on <branch>)`); otherwise the start reaches main with the next merge, `warp:sync`, or checkpoint.
- The run state stays current between publishes: every supervise pass rewrites `BOARD.md`, `board.html`, `STATUS.md` and `status.json` from the live beam, and each publish rewrites them first, so a merge carries every transition up to it.
- How the run state reaches the base branch, now in README, CONFIG, COMMANDS and STATE: the merge commit (above), or one `Warp state: <run> run` commit of `.warp/runs/<run>/` built on origin's base branch and pushed straight to it (`warp:sync`, `pushStateNew`, checkpoints, and a merge that fell back). It never goes through a ticket branch or a pull request.
- Docs: README (config table: `pushStateNew`, `stateInMerge`), CONFIG, COMMANDS, LIFECYCLE (the merge lines), MERGE-POLICY, RUNBOOK, STATE (`pr.stateInMerge`), the warp skill and the example config.

## 1.6.20

- New: `mergeMethod` picks how a pull request is merged, and the default is now `merge`: a merge commit, so each ticket branch joins the base in a git graph. Before this every pull request was squash-merged, and a squashed branch dead-ends in the graph (PR #24's head `8a69213` became `5796d14` on main), which made merged tickets look unmerged. `squash` keeps the old behavior, and `rebase` replays the commits. It goes to `gh pr merge --<method>`, the merge queue, the `merge: MUST DO` line for the GitHub MCP (`merge_method <method>`), `/warp-proceed`, and `beam.py set --merge-method`. A local merge (`provider.py merge-local`) makes a merge commit or a squash; `rebase` gets a merge commit there, so a branch a Shuttle may still use is never rewritten. `pr.mergeMethod` records the method used.
- New: `deleteBranchOnMerge` (default `false`) deletes a merged ticket's branch on origin, and its local branch when no worktree holds it, once the merge is confirmed: `merge: branch deleted <id> <branch>`, or `merge: branch not deleted <id> <branch>: <why>`. Never the base branch. A branch already gone counts as deleted. `pr.branchDeleted` records it.
- New: the run state is published to the base branch right after a merge (`state: published (merged WE-01)`) and when `checkout.py launch` creates a ticket's branch (`state: published (started WE-02 on warp/edit/WE-02-WAR-64)`), so main shows a ticket in progress as soon as it starts and merged as soon as it merges. Before this the run state on main was pushed only on start, stop and checkpoints, and after a merge it waited for the parent's `beam: push`, which the edit run's parent skipped: WE-01 and WE-03 were merged on GitHub while the published state still showed them in review and queued. `publishOnChange: false` leaves it to the parent. `state: not published (...)` names why it failed; the pass goes on.
- New: `warp:sync [run]` in Slack or Teams pushes the run state to the repo now. The parent rewrites the board and status files from its live beam, commits the run state (beam, journal, board, status, stats, ticket folders) to the base branch and pushes it, and posts `Run state pushed to main at <sha> (.warp/runs/edit/): 3 merged, 2 review, 9 queued.`, or why it could not. It works with `publishOnChange: false`. Every run answers a bare `warp:sync`; `warp:sync edit` names one.
- Docs: README (the config table, merge policy, pipeline, Slack messages, several runs, run control), CONFIG, COMMANDS, CONNECTORS, GUIDE, LIFECYCLE (one pass: the Bugbot lines, the pass update, `run: stopped`, the publish; the wait's Bugbot summary), MERGE-POLICY, RUNBOOK, STATE (`.warp/notify-pass.json`, `pr.mergeMethod`, `pr.branchDeleted`, `pr.heraldUrl`, `statusDigest`), the warp skill and `/warp-proceed` now describe 1.6.18 through 1.6.20, and no longer say pull requests are squash-merged or that the parent pushes the beam after a merge.

A generation now hands off before that: `listenerMaxReads` is 4 (was 60) and `listenerSlowSeconds` is 120 (was 60). - The parent writes `listener.parentSeenAt` from `parent-exit --wait` and from `supervise`. A stamp older than `listenerOrphanMinutes` (default 5) makes the listener exit `orphaned` and write the return stamp. A stale heartbeat does not start a replacement. The return stamp does (`polled`, `rotated`, `orphaned`, `stopped`), and only when no holder is live. Lease expiry bumps the generation and does not start the next copy in the same moment.
- `inbound.py wait` sleeps in Python in 2-second steps. `listenerFastSeconds` (15) after a cycle that queued a command, `listenerSlowSeconds` (60) after an empty read. It returns early on halt, a lease mismatch, an orphan, or rotation. Pause and stop reap the listener within about 2 seconds. A read already in flight finishes, then the next poll reaps it. `pollSeconds` is only the parent-wait cap.
- The parent wait also wakes on the inbound queue (`pass: command`) and on the return stamp (`pass: return`). Acks stay deduped by Slack ts: `inbound: duplicate` writes no second ack.
- Rotation at `listenerMaxMinutes` or `listenerMaxReads` (default 60), whichever comes first, prints `listen: rotate` and writes the return stamp. The repair sweep and `listenerStaleMinutes` no longer start a listener. `listenerStaleMinutes` is retired.
- `listen: stopped` idles only the supervise pass that still had the generation out, or when the run should not listen. A later pass with the same line starts the next generation when tickets are still open. Hold lines name the reason: `listener: hold reason=live` and `listener: hold reason=await-return`. Start prints `listener: not started. The next supervise issues it.`

A Shuttle does one step of one ticket and returns one line. The listener does one poll and returns one line. Nothing depends on a Cursor hook: plugin hooks do not run on cloud runners, and every check is a script that a command, a skill, or a prompt runs.

Every worker prompt carries `agent: <id>`, the contract (one step, one result line, never start another agent, never subscribe, set a timer, loop, sleep, or wait on a pull request, CI, Bugbot, Slack, or an approval), and the reap command. A worker woken by something that is not a new step from the parent runs the reap check and returns.

Every registry row is ended and marked halted, every Shuttle slot is freed, the listener's poll is closed (`halt: paused agents=<n>`), and the state is pushed. The agent running the command and this run's parent are skipped. Without the key it prints one link per cloud agent. The parent starts one `warp-listen` subagent in the foreground. Two Warp runs in one channel, in one repo or in different repos, are told apart.
